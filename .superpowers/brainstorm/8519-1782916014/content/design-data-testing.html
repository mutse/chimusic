Data Flow, Error Handling, and Verification

The implementation should make local playback reliable first, then reshape the product surface around that reliability.

Local-only runtime flow
User imports files / folders
Importer reads metadata and artwork
Controller builds local collections
Repository persists snapshot locally
User searches / browses / plays
Player updates queue and position
History records play count and resume
Discover refreshes from local signals

State cleanup

Stop restoring users or remote snapshots. Remove visible use of auth, cloud sync, subscription, Pro, and AI quota state. Keep repository compatibility only where needed to avoid breaking existing saved data.

Error handling

Import errors, missing files, failed playback preparation, unavailable tracks, and failed metadata reads become local status messages with recovery actions: retry import, relink file, remove missing track, or continue browsing.

Persistence

Playback history, recent searches, likes, saved local collections, queue, current track, position, shuffle, repeat, and theme continue to persist locally through SQLite and the JSON snapshot fallback.

Verification

Controller tests cover local search, library filters, queue playback, history persistence, restore behavior without users, and absence of cloud/auth actions. Widget tests cover no login/cloud/Pro text in the primary shell.

Acceptance checks

  • Fresh install shows import-first local music onboarding.
  • Imported music creates Discover, Search, Library, and Player content.
  • Playback history survives restart locally.
  • No visible sign-in, cloud sync, membership, Pro, AI quota, comments, follows, or social feed.

Deferred

  • Network streaming catalog.
  • Account-based social features.
  • Cloud backup or cross-device sync.
  • Deep deletion of all legacy model fields if that risks migration churn.
